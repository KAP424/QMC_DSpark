和原理有关，但不是“原理错了”，而是**DSpark 优化的那个变量，在当前场景里根本不在瓶颈上**。拆开讲。

## 1. 投机解码的收益恒等式

设：

- `C` = 目标模型一次前向（1 token）的墙钟成本
- `V(L)` = 一次验证 L 个 token 的成本
- `D` = 一次 draft 的成本
- `n` = 每轮接受的 draft 数（输出 `n+1` 个 token，含 bonus）

加速比就是：

```
speedup = (n+1) · C / (V(L) + D + 回滚/补数)
```

要让这个式子 > 1，必须满足 **`n+1 > (V + D) / C`**。所以投机解码的收益从来不是由“接受率”单独决定的，而是由**接受率与「每轮成本 / 单次前向成本」之比**的竞赛决定。

这个比值在不同成本结构下差别巨大，分三种情况：


| 成本结构                               | 单 token 成本主要花在 | V(L)/C       | 需要 n 才能回本    |
| -------------------------------------- | --------------------- | ------------ | ------------------ |
| **算力受限**（大模型、小 batch）       | matmul                | ≈ 1         | n > ~0（几乎稳赚） |
| **带宽受限**（中等模型）               | 权重读取              | 1 ~ 1.3      | n > 0.3            |
| **调度受限**（小模型 / 未优化 kernel） | CPU 发射 + Python     | ≈ 2（见下） | n > 1.6            |

**DSpark、Eagle3、Medusa 全部都是“用算力换串行步数”**：与其顺序做 5 次前向，不如一次并行验证 5 个位置。这个交易成立的前提是——**你省下的串行步骤成本 ≫ 你多花的那次调用的固定成本**。算力受限时固定成本小，稳赚；调度受限时固定成本就是全部成本，交易亏损。

## 2. 0.8B 在这台机器上正好掉进“调度受限”区

实测数据：


| 项                     | 数值           | 说明                                          |
| ---------------------- | -------------- | --------------------------------------------- |
| GPU 纯计算（每 token） | ~4 ms          | 权重 1.75 GB ÷ 864 GB/s ≈ 2.0 ms 的理论下限 |
| CPU 侧开销（每 token） | 19.9 ms        | 1400 次 kernel 发射 + GDN 的 Python 逐头循环  |
| 一次前向总耗时         | 18.4~20.5 ms   | **GPU 空闲约 80%**                            |
| 验证 1 / 8 token       | 18.4 / 30.5 ms | 边际成本仅 ~1.7 ms/token                      |

**模型越小，这个结构越糟。** 8B 模型 bf16 是 17.6 GB，光权重读取就要 20 ms，那 19 ms 的 CPU 开销就只占一半，V(L)/C 会接近 1；而 0.8B 的权重读取只要 2 ms，固定开销占了绝对主导。

这直接回答“为什么小模型没有收益”：**小模型的单 token 计算便宜到被固定开销淹没，于是投机解码省不掉任何串行时间，只是多买了一次固定开销。**

## 3. 这个模型还额外收了一笔“回滚税”

即使按 H100 + CUDA graph 把固定开销压到 5 ms，我这里仍有一个结构性亏损，来自 **GatedDeltaNet 的循环状态不可裁剪**：

- 24 层里 18 层是线性注意力，`is_croppable == False`，`crop` 只能回滚卷积状态，不能回滚 `recurrent_states [1,16,128,128]`；
- 所以**部分接受**时必须 deepcopy 缓存 + 把接受的前缀重放一遍（多一次前向）；
- 而**全部接受**时，因为验证前向的最后一个位置已经被草稿占满，bonus token 还要单独一次前向。

结果就是**每轮稳定 2 次目标前向**，V ≈ 1.63C。代进不等式：

```
n + 1 > 1.63 + 1 = 2.63   →   n > 1.63
```

而 MTP 头的实测接受数是 **n = 1.5 ~ 1.72**——正好卡在回本线上，所以表现为“差不多持平、略亏”。这不是巧合，是算式决定的。

**这一点恰好体现了 DSpark 论文和这个 0.8B 模型的关键差异**：论文的目标是 DeepSeek-V4 这种大型 MoE，验证一次的开销远小于分摊到多个 token 的收益，而且它们没有这种“循环状态不可回滚”的税（或者用专门的 kernel 处理了）。

## 4. DSpark 自己的三个机制，各自假设了什么

这是“和原理有关”的部分——**DSpark 的三个机制都在优化接受长度的「形状」，但它默认分母侧的固定开销已经足够小**：


| 机制                      | 它优化的东西                                                                    | 在本场景为什么失效                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 半自回归 drafter          | 让接受长度的衰减变慢（对抗 parallel drafter 的 suffix decay）                   | **有效但不够**：MTP 单步 top-1 只有 0.42，实测曲线陡降，n 只有 1.63                                  |
| 置信度调度验证            | 按`argmax E[tokens]/t_verify(L)` 选 L                                           | **退化了**：本机 t_verify 在 L≥2 后是平的（30 ms），调度器永远选最大 L（实测 pick=7），等于没有调度 |
| 硬件感知 prefix scheduler | 按 SPS(batch) 曲线分配**全局**验证预算，缓解高并发下固定长度验证浪费 batch 容量 | **前提不存在**：batch=1 时没有“容量”可分配；它解决的是并发吞吐前沿问题，不是单请求延迟             |

特别注意第二行：那个“验证边际成本几乎为零”的现象（L=2 到 L=8 都是 30 ms），**正是 DSpark 依赖的“免费午餐”**。它确实存在，但只是算力层面的免费；**调用次数不是免费的**，而我们的每一次前向都带着 18 ms 的调度开销。

原论文的收益表述也能印证这一点：它强调的是“**matched throughput level** 下 per-user 加速 60–85%”，也就是**在相同聚合吞吐下**把空闲容量换成单用户速度——这是**高并发下的容量再分配**，而不是“batch=1 的单请求延迟优化”。对 0.8B + batch=1，没有空余容量可再分配。

## 5. 要多强的 drafter 才能转正

把 `V ≈ 30 ms`（恒定）、`C ≈ 16.9 ms` 代进去：

```
speedup ≥ 1.5  ⇔  (n+1) · 16.9 ≥ 1.5 · (30 + 18.4)  ⇔  n ≥ 3.36
```

而 `n - 1 ≈ p + p² + p³ + …`（p 为单步存活率，K=8 时验证成本不变，所以长 K 是“免费”的）。解出来：


| 单步存活率 p          | K=8 时的 n | 相对基线  |
| --------------------- | ---------- | --------- |
| 0.42（当前 MTP 实测） | 1.63       | ×0.75    |
| 0.55                  | 2.2        | ×1.05    |
| **0.65**              | **2.85**   | **×1.3** |
| 0.75                  | 3.9        | ×1.6     |

**所以门槛是：需要一个单步存活率 0.65 以上、且衰减很慢的 drafter。** 而“把衰减压慢”正是 DSpark 半自回归头的设计目标——只是我们这里只有一个 20M 的 MTP 层可用，能做到 0.42 已经接近它的上限，没有 Eagle3 那种专门的多 token draft 头。

## 6. 所以，结论

和原理有关，分三层：

1. **通用层（占大头）**：投机解码是“用算力换串行步数”的交易。小模型在调度受限的机器上算力本来就过剩，**没有东西可换**，反而多付了一次前向调用。这是 ScalingLaw 级别的结构问题——原论文选 4B/8B/14B 作为离线验证集，选 100B+ MoE 作为生产环境，不是偶然。
2. **模型结构层（本模型特有）**：混合线性注意力的循环状态不可回滚，强制每轮 2 次前向，把回本门槛从 n>1 抬到 n>1.63。
3. **DSpark 原理层**：它的半自回归头确实在对的方向上（压慢衰减），但置信度调度和 prefix scheduler 优化的都是“并发容量”，在 batch=1 的单请求场景里退化成空转——我实测 `pick()` 选 7 和固定 K=2 吞吐一样，就是这个原因。

如果想在这个模型上真正看到 DSpark 的收益，优先级应该是：**先把那 20 ms 的调度开销打下去（CUDA graph / 融合 kernel / flash_attn），再谈 drafter**——因为只有分母降到和算力成本同量级，接受率才有意义。

# 但是我可以给Target model不同的 bonus token（边缘均匀分布、Batch内联合分布 随机数），一下多个并行 Dspark 向前

生成 Draft 时候在用 Gumbel-max 再加一个边缘均匀分布、Batch内联合分布随机数得到多个Draft

我的设想是同一个 prompt，输入 target model：

1. 得到bonus token的概率后，给多个不同的随机数 $u^b_i\in Uniform[i/N_b,(i+1)/N_b]$ , 用 CDF 的逆函数得到不同的 bonus token
2. 在把相同的target model的 隐藏层 + 不同 bonus token 输入 Dspark。得到最后的 Draft 块概率分布，再对每种 bonus token 给多个不同的随机数 $u^d_i\in Uniform[i/N_d,(i+1)/N_d] $，在通过 Gumbel 得到 CDF 逆函数，最后输出多个不同的草稿。
3. 随后将这 $N_b\times N_d$ 种 draft 交给 target 模型验证。这些 draft 会存在贡献的 token 块，这个特点需要好好利用，这样可以减少计算量。
4. 假设 draft 块的 token 长度是 L，由于我们有非常多种的draft，所以对于接受长度低于 $L/2$ 的 draft 可以直接选择丢弃，这样也能加速最后的 rollout 生成速度
5. 进一步我们可以通过 target model 的验证情况来同步训练 dspark 模块
