## 三、Verify 脚本（0/1 打分）

每个域一个判定函数，输入 `(prompt_metadata, response_text)`，输出 `{0,1}`。现有 `test/test_domain_speed_acc.py` 已有 countdown 和 1d_arc 的实现，补 maze 和 sudoku：

### 3.1 Maze verify

Maze 的 prompt 里 S 是起点、E 是终点，`sol` 是参考最短路径。Verify 判定 response 是否给出一条从 S 到 E 的合法路径：

- 解析 response 中的路径字符串（仅含 `URDL` 字符）
- 从 S 出发，按字符逐步移动
- 每步必须落在非 `*` 格子（`.` 或字母）
- 最终必须到达 E
- 不要求与参考 `sol` 相同（任何合法路径都给 1 分）

```python
def check_maze(resp, maze_str, sol):
    grid = [list(r) for r in maze_str.splitlines()]
    H, W = len(grid), len(grid[0])
    # 找 S 和 E
    sr = sc = er = ec = None
    for i in range(H):
        for j in range(W):
            if grid[i][j] == 'S': sr, sc = i, j
            if grid[i][j] == 'E': er, ec = i, j
    # 从 response 里提取第一个纯 URDL 的子串
    path = ''.join(c for c in resp if c in 'URDL')
    if not path: return False
    r, c = sr, sc
    for m in path:
        if   m == 'U': r -= 1
        elif m == 'D': r += 1
        elif m == 'L': c -= 1
        elif m == 'R': c += 1
        if not (0 <= r < H and 0 <= c < W): return False
        if grid[r][c] == '*': return False
        if (r, c) == (er, ec): return True
    return (r, c) == (er, ec)
```

### 3.2 Sudoku verify

判定 response 是否给出完整的 9×9 合法解（与 `sol` 等价即可，不要求字符完全一致）：

```python
def check_sudoku(resp, sol):
    # 提取 response 中的 9 行，每行 9 个数字
    nums = re.findall(r'\d', resp)
    if len(nums) < 81: return False
    grid = [nums[i*9:(i+1)*9] for i in range(9)]
    # 每行、每列、每 3×3 宫都是 1..9
    rows = [set(grid[i]) for i in range(9)]
    cols = [set(grid[r][c] for r in range(9)) for c in range(9)]
    boxes = [set(grid[3*i+r][3*j+c] for r in range(3) for c in range(3))
             for i in range(3) for j in range(3)]
    return all(s == set('123456789') for s in rows + cols + boxes)
```

def verify(it, resp):

## 四、Target model 训练（GRPO）

### 4.1 超参（参照 TRL GRPO / quasimotto maze-grpo 实测配置）

GRPO 不逐 prompt 更新，而是 **mini-batch + 梯度累积 + rollout 复用**。参照 quasimotto 的 maze/sudoku GRPO 配置（基于 TRL `GRPOTrainer`），这套超参在同类小模型 RL 上已被验证可用：


| 超参                          | quasimotto 值 | 含义                                         |
| ----------------------------- | ------------- | -------------------------------------------- |
| `num_generations` (G)         | 8             | 每个 prompt 采 G 条 rollout（组大小）        |
| `per_device_train_batch_size` | 32            | 每个 device 每个 mini-batch 的 prompt 数     |
| `gradient_accumulation_steps` | 4             | 累积 4 个 mini-batch 后再 optimizer.step     |
| `num_iterations`              | 2             | 每个 batch 的 rollout 被复用 2 次 PPO 梯度步 |
| `epsilon`                     | 0.2           | PPO clip 范围                                |
| `beta`                        | 0.01          | KL 惩罚系数                                  |
| `scale_rewards`               | none          | advantage = r_i − μ_g（不除以 σ）         |
| `importance_sampling_level`   | sequence      | token 级 importance 权重（PPO ratio）        |
| `learning_rate`               | 2e-6          | cosine 调度，warmup 5%                       |
| `temperature`                 | 1.0           | rollout 采样温度                             |
| `max_completion_length`       | 256           | 单条 rollout 最大 token 数                   |
| `adam_beta1 / beta2`          | 0.9 / 0.95    | AdamW                                        |
| `weight_decay`                | 0.01          |                                              |
| `max_grad_norm`               | 1.0           |                                              |
| `bf16`                        | true          | 训练精度                                     |

**一次 optimizer step 处理的 prompt 总数** = `per_device_train_batch_size × gradient_accumulation_steps × num_devices` = 32 × 4 × N = 128N（单卡 128）。每条 prompt G=8 条 rollout，所以每个梯度步基于 128N × 8 = 1024N 条 completion。这与逐 prompt 更新差几个数量级，也是 GRPO 稳定的关键。

### 4.2 组内相对优势

每个 prompt 的 G 条 rollout 组成一组，组内归一化得到 advantage（`scale_rewards=none` 时只去均值）：

$$
\hat{A}_i = r_i - \mu_g, \quad \mu_g = \frac{1}{G}\sum_{j=1}^{G} r_j
$$

其中 $r_i \in \{0,1\}$ 是第 $i$ 条 rollout 的 verify 分数。若 $\sigma_g = 0$（全 0 或全 1），整组跳过——无信号，更新只会放大噪声。

### 4.3 PPO clip 目标（不是 vanilla policy gradient）

TRL GRPO 使用 PPO 风格的 clipped objective，不是原始的策略梯度。对每条 rollout 的每个 token：

$$
\mathcal{L}_{\text{GRPO}} = -\mathbb{E}_{i,t}\left[\min\left(\rho_{i,t}\hat{A}_i,\; \text{clip}(\rho_{i,t}, 1-\epsilon, 1+\epsilon)\hat{A}_i\right)\right] + \beta \cdot \text{KL}\left(\pi_\theta \| \pi_{\text{ref}}\right)
$$

其中 $\rho_{i,t} = \pi_\theta(y_{i,t}\mid\cdot)\,/\,\pi_{\theta_{\text{old}}}(y_{i,t}\mid\cdot)$ 是 importance ratio（当前策略 vs rollout 时刻策略）。`num_iterations=2` 表示同一 batch rollout 会做两次梯度步——第二次的 $\rho$ 相对第一次更新后的策略计算，PPO clip 防止策略偏离过远。这是 GRPO 相比朴素 policy gradient 更稳的根本原因。

KL 项约束当前策略 $\pi_\theta$ 与冻结的参考策略 $\pi_{\text{ref}}$（训练初始 checkpoint）之间，$\beta=0.01$。TRL 默认用 k3 估计。

### 4.4 rollout 生成（DSpark + 多分支引擎）

**关键映射**：GRPO 的 `num_generations=8` 与 DSpark 多分支引擎的 `branches=8` 完全对齐——一次 DSpark 多分支前向就产出 GRPO 所需的整组 rollout：

```python
# 一个 prompt 的 G=8 条 rollout —— 一次 DSpark 前向得到
chains = eng.generate_branches(prompt_ids, max_new_tokens=256,
                                n=ND, branches=8, mode='stratified',
                                return_all=True)
# chains: 8 个 (token_ids, stats) —— 即 GRPO 的一个 group
```

**批量并行**：mini-batch 内 32 个 prompt 不是逐个生成，而是 pad 成 batch 后一起送入 target 模型生成（quasimotto 用 transformers `generate` + `custom_generate=qmc_sample` 批量采样）。我们的 `generate_branches` 目前一次处理单 prompt，需要扩展为批量接口（32 个 prompt 一起送入），或先顺序循环——前者更高效，是后续工程优化方向。

### 4.5 一次 optimizer step 的完整流程

```python
opt.zero_grad()
for accum in range(gradient_accumulation_steps):       # 4 次
    # 1. 取一个 mini-batch: 32 个 prompt
    prompts = next(dataloader)
    # 2. 每个 prompt 生成 G=8 条 rollout（共 32*8 = 256 条 completion）
    rollouts = [eng.generate_branches(p, max_new_tokens=256, branches=8, ...) for p in prompts]
    rewards  = [[verify(it, tok.decode(c[0])) for c in chain] for chain in rollouts]
    # 3. 每个 group 的 advantage（scale_rewards=none: 不除 sigma）
    advs = []
    for r in rewards:
        mu = sum(r)/len(r)
        advs.append([x - mu for x in r])
    # 4. 计算 log-prob：当前 pi_theta / 冻结 pi_ref / rollout 时 pi_old
    logp     = compute_logprobs(model,      rollouts)   # 当前 pi_theta
    logp_ref = compute_logprobs(model_ref,  rollouts)   # 冻结 pi_ref（KL 用）
    logp_old = logp.detach()                             # rollout 时的策略
    # 5. PPO clip loss + KL；num_iterations 复用 rollout 做 2 次梯度步
    for it in range(num_iterations):                     # 2 次
        ratio  = (logp - logp_old).exp()
        surr1  = ratio * advs
        surr2  = ratio.clamp(1-eps, 1+eps) * advs
        pg     = -torch.minimum(surr1, surr2).mean()
        kl     = (logp_ref.exp() * (logp_ref - logp)).sum(-1).mean()
        loss   = pg + beta * kl
        (loss / gradient_accumulation_steps).backward()
        if it < num_iterations - 1:
            logp = compute_logprobs(model, rollouts)    # 参数变了，重新算
opt.step()
```

注意：rollout 只生成一次（开销最大），但被 `num_iterations=2` 次梯度步复用；grad 按累积步数归一化；KL 用参考策略（训练前冻结）。

### 4.6 Target 训练约束

- **Target 参数参与训练**（与 §5 的 Draft 训练相反——Draft 训练时 Target 是 frozen 的）
- 启动前复制 `parameter/target/Qwen3.5-0.8B-Base-original/` 到 `parameter/rl/<dataset>/target_init/`，作为 $\pi_{\text{ref}}$ 和训练起点——**不动 SFT 原始 checkpoint**，便于实验失败回滚
- lr=2e-6，cosine，warmup 5%，bf16，grad clip 1.0
- 每 100 步存 checkpoint，保留最近 20 份

## 五、Draft model 训练（Accept/Reject 信号）

### 5.1 信号来源

DSpark 验证时，对每个 draft slot $k$，Target 模型给出概率 $p_k$，Draft 给出 $q_k$：

- **接受**（accept）：Target 采样得到的 token 与 Draft 采样的 token 一致，或通过 rejection sampling 接受
- **拒绝**（reject）：Target 采样得到的 token 与 Draft 不一致，被修正（correction）

这个信号已在 `dspark_fast.py:_accept_multi` 中产生，每个 slot 一个二值标记。

### 5.2 训练目标

Draft 模型目标是让 $q_k$ 逼近 $p_k$，使 accept 概率最大化。两种损失组合：

**(a) 软标签蒸馏**（对每个 slot）：

$$
\mathcal{L}_{\text{distill}} = \sum_k w_k \cdot \text{KL}(q_k \| p_k)
$$

权重 $w_k = \exp(-(k-1)/\gamma)$ 与现有训练一致。

**(b) 拒绝 token 的惩罚**（对 reject slot）：

对被拒绝的 slot，直接用 Target 采样的 token 作为硬标签，做 CE：

$$
\mathcal{L}_{\text{reject}} = \sum_{k \in \text{rejected}} w_k \cdot \text{CE}(q_k, x^*_k)
$$

其中 $x^*_k$ 是 Target 在该 slot 实际采样的 token（correction token）。

**(c) 总损失**：

$$
\mathcal{L}_{\text{draft}} = \alpha \cdot \mathcal{L}_{\text{distill}} + (1-\alpha) \cdot \mathcal{L}_{\text{reject}} + \mathcal{L}_{\text{conf}}
$$

推荐 $\alpha = 0.7$（蒸馏为主，reject 信号为辅），$\mathcal{L}_{\text{conf}}$ 是现有的 confidence head BCE。

### 5.3 rollout 复用

**关键**：Draft 训练信号和 Target GRPO rollout 来自同一次 `generate_branches` 调用，不需要额外前向：

```python
# 同一次调用同时产出两条训练信号
chains, per_slot_accept = eng.generate_branches(
    prompt_ids, max_new_tokens=512, branches=B,
    mode='stratified', return_all=True,
    return_accept_mask=True     # 新增：返回 (B, rounds, n) 的 accept mask
)

# Target 训练用 chains 做 GRPO
# Draft 训练用 per_slot_accept 做 reject-CE + 全 slot KL
```

需要在 `dspark_fast.py:generate_branches` 中新增 `return_accept_mask` 选项，把 `_accept_multi` 返回的 `k`（接受长度）和 `corr`（correction token）暴露出来。

### 5.4 Draft 训练约束

- **Draft 模型参数参与训练，Target 模型 frozen**（与现有 PB 训练一致）
- 现有 SFT 阶段的 `dspark_loss.py` 和 `pb_train_v2.py` 可直接复用，新增 reject-CE 项即可
- lr = 2e-4（与现有域扩训练一致）

## 六、交替训练 schedule

两个模型不能同时反向（共享 forward 但梯度会耦合），采用**交替更新**：

```
for step in range(total_steps):
    # 1. rollout（共享）
    chains, accept_mask = eng.generate_branches(prompts, B=8, return_accept_mask=True)

    # 2. Target GRPO step（Target 可训练，Draft frozen）
    target_loss = grpo_loss(chains, rewards, model)
    target_loss.backward(); target_opt.step()

    # 3. Draft step（Draft 可训练，Target frozen）
    draft_loss = distill + reject_ce + conf_bce
    draft_loss.backward(); draft_opt.step()
```

每个 step 一次 rollout，两次反向传播。rollout 的 forward 结果可缓存复用（Target 在 GRPO loss 里需要 response 段的 logits，Draft 在 distill 里需要 hidden states——都是同一个 forward 的不同输出）。

## 八、验证与评测

每个 step 在 val 集上评测：

1. **正确率**（verify 给 1 的比例）—— Target RL 的主指标
2. **τ**（平均接受 token 数）—— Draft 质量指标
3. **tok/s**（端到端加速比）—— 工程指标

预期：Target RL 训练后正确率提升（数学/路径推理变强），Draft 训练后 τ 在该域进一步提升，两者叠加让加速比从 ~1.8× 升到更高。
